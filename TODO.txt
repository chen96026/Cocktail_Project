# 主線：把資料搬到 YAML，讓專案不用連 MySQL 也能跑 —— 已完成（2026-10-02）

## 現在的運作方式

    git clone → mvn spring-boot:run → 資料自動長回來

- 預設 profile：H2 記憶體資料庫，啟動時 DataSeeder 讀 src/main/resources/seed-data.yaml 載入
- mysql profile：mvn spring-boot:run -Dspring-boot.run.profiles=mysql
  連本機 MySQL（設定在 application-mysql.properties），不載入 YAML
- 圖片維持 Cloudinary，新增酒譜上傳圖片時需要網路 + 金鑰


## 決定紀錄

1. H2 dependency：加（runtime scope，版本跟 Spring Boot BOM）
2. 匯出功能：先不做，要改資料就直接改 YAML
3. Cloudinary：維持雲端，不做 local 版


## 初始資料來源

由 2026-09-28 的 MySQL dump 直接轉成 seed-data.yaml
- 48 杯酒 / 200 筆材料 / 93 筆基酒關聯 / 48 組四維度組合
- 用 SnakeYAML 讀回逐欄比對 SQL 原始資料，零差異
- 舊資料表 member（會員功能已移除）與未被使用的「待分配」組合沒有轉入


## seed-data.yaml 格式

cocktail:
  seed:
    recipes:
      - enTitle: Screwdriver
        zhTitle: 螺絲起子
        image: https://res.cloudinary.com/<CLOUD_NAME>/image/upload/xxx.jpg
        method: |-
          第一段介紹
          第二段介紹
        baseWines: [Vodka]
        materials:
          - name: 伏特加
            quantity: 45ml
          - name: 柳橙汁
            quantity: 120ml
        combination: {mood: 普通, taste: 酸, tone: 暖, drunk: 微酣}

說明：
- 四維度組合直接內嵌在每杯酒下面，不用另外維護 combination_option
- 沒有分配組合的酒譜，combination 那行省略即可
- image 存 Cloudinary URL，換電腦照樣看得到圖
- 基酒名稱要跟前端 constants/options.js 的 BASE_WINES value 一致


## 日常工作流程

  啟動：     mvn spring-boot:run

  新增 / 編輯 / 刪除酒譜、分配組合：
    1. 直接改 seed-data.yaml
    2. 重啟後端，畫面確認
    3. commit

  ※ 網頁 UI 上的新增、編輯、刪除都能正常操作，但只存在 H2 記憶體，
    重啟後回到 YAML 的狀態
  ※ 新酒譜的圖片：先從網頁新增一次拿到 Cloudinary URL（或到 Cloudinary 後台上傳），
    再把 URL 填進 YAML 的 image

## API 路徑（2026-10-02 改為 REST 風格，前綴 /lastwine 給 vite proxy 用）

  GET    /lastwine/recipes?baseWine=Gin,Rum&keyword=琴   酒譜列表；基酒要全部符合、關鍵字比對中英文名稱，
                                                          兩者取交集；不帶或 baseWine=All 為全部
  GET    /lastwine/recipes/{id}                          單一酒譜
  GET    /lastwine/recipes/{id}/detail                   詳細頁（含四維度組合）
  POST   /lastwine/recipes                               新增（multipart：recipe JSON + image）
  PUT    /lastwine/recipes/{id}                          更新（multipart，image 可省略）
  DELETE /lastwine/recipes/{id}                          刪除
  GET    /lastwine/selector?mood=&taste=&tone=&drunk=    四維度篩選器
  GET    /lastwine/combinations                          組合列表
  POST   /lastwine/combinations                          新增組合
  GET    /lastwine/recipe-combinations                   後台：酒譜與組合對照表
  PATCH  /lastwine/recipe-combinations                   後台：整批分配組合
  Swagger：/swagger-ui/index.html

# 家裡那台 MySQL 的資料搬移（mysql profile 才需要，H2 不用）
################################################################################

2026-10-02 起，酒譜與組合的對應從 combination_option 中介表改成 recipe.combination_id。
ddl-auto=update 會幫 recipe 加欄位，但不會搬資料。建議在新版「啟動前」做：

[ ] 0. 備份：mysqldump -u <USER> -p cocktail > cocktail-before-migration.sql

[ ] 1. 檢查有沒有一杯酒對到多組（理論上 0 筆；有的話下面取 option_id 最大＝最後一次分配的）
       SELECT fk_recipe_id, COUNT(*) cnt FROM combination_option
       GROUP BY fk_recipe_id HAVING COUNT(*) > 1;

[ ] 2. 加欄位（型別先用 SHOW CREATE TABLE combinations; 確認，要跟 combinations.combination_id 一樣，
       UNSIGNED 也要照抄，不然 FK 建不起來）
       ALTER TABLE recipe ADD COLUMN combination_id INT NULL;

[ ] 3. 搬資料
       START TRANSACTION;
       UPDATE recipe r
       JOIN combination_option co ON co.fk_recipe_id = r.recipe_id
       JOIN (SELECT fk_recipe_id, MAX(option_id) option_id
             FROM combination_option GROUP BY fk_recipe_id) latest
         ON latest.option_id = co.option_id
       SET r.combination_id = co.fk_combination_id;
       -- 第 4 步檢查都 OK 再 COMMIT，否則 ROLLBACK
       COMMIT;

[ ] 4. 檢查
       -- 兩個數字要相同
       SELECT COUNT(DISTINCT fk_recipe_id) FROM combination_option WHERE fk_combination_id IS NOT NULL;
       SELECT COUNT(*) FROM recipe WHERE combination_id IS NOT NULL;
       -- 指到不存在組合的資料要 0 筆（不然 Hibernate 加 FK 會失敗）
       SELECT r.recipe_id FROM recipe r LEFT JOIN combinations c ON c.combination_id = r.combination_id
       WHERE r.combination_id IS NOT NULL AND c.combination_id IS NULL;

[ ] 5. 用 mysql profile 啟動新版：log 沒有 DDL 錯誤、SHOW CREATE TABLE recipe; 有 combination_id → combinations 的 FK，
       畫面上篩選器、詳細頁、Admin 都正常

[ ] 6. 確認沒問題、備份留好之後 DROP TABLE combination_option;
       （留著不會壞事，但已經是不會再更新的死資料）

另一種做法：先啟動讓 Hibernate 自己加欄位和 FK，再跑 1、3、4（跳過 2）。
缺點是啟動到跑完 UPDATE 之間，篩選器查不到任何酒。

# 其他已知待辦（依建議優先順序）

[ ] 2. JDK 版本 —— 決定維持 java.version=21
       這台筆電系統 JDK 是 17，mvn 需要指定 JDK 21 才能跑：
       裝 JDK 21，或直接用 IntelliJ 內建的 JetBrains Runtime 21（JAVA_HOME 指過去即可）
       IntelliJ 拉下 2026-10-02 這批 commit 後要 Rebuild 一次（package 改名、刪了 CombinationOption，
       target/ 裡的舊 class 會被當成 Entity 掃進去）

[ ] 6. Entity 的 getter/setter 樣板
       Recipe / Combination / Material / BaseWine 四支，扣掉欄位宣告幾乎都是樣板
       Entity 不能用 record（JPA 要無參建構子 + 可變），只能靠 Lombok @Getter @Setter
       → 需要新增 dependency，先確認

[ ] 7. Admin 後台的組合過濾條件
       原本 !recipes.some(r => r.currentCombination?.combinationId === ...) 因為
       後端 DTO 是平的 combinationId，這個 filter 從來沒生效過，拆元件時已移除，
       維持「所有組合都顯示」的現狀行為。
       如果原意是「已被指派的組合不要再出現」，要改成 r.combinationId 比對，
       但要注意副作用：組合全配完後下拉會變空，就不能再改配對了
       （比較合理的版本：排除被別的調酒占用的組合，但保留自己目前那一個）

[ ] 8. 設定檔分 profile
       datasource 已拆成預設（H2）/ mysql 兩個 profile
       剩 show-sql=true、Swagger 永遠開著，可以再拆 local / prod

[ ] 14. Cloudinary 孤兒圖（量小可接受）
       重名已在上傳前擋掉，但上傳後才存檔失敗（例如兩邊同時新增同名、DB 出錯）時圖片仍留在雲端；
       addRecipe 在交易裡上傳，上傳期間會佔著一條 DB 連線

[ ] 15. 資安（目前先略過）：application.properties 的 Cloudinary api_key / api_secret 是明文且已進 git
       → 改用環境變數，並到 Cloudinary 換一組 key

[ ] 16. mysql-connector-j 寫死在 8.0.33（compile scope）
       8.0.33 有已知 CVE（CVE-2023-22102，8.2.0 修掉）；拿掉 <version> 改由 Spring Boot BOM 管版本，
       scope 改 runtime。只有 mysql profile 會用到，升完要回家那台實際連一次 MySQL 驗證
       → 依賴升級，先確認

[ ] 17. Spring Boot 3.5.16 是 2026-06 發布、3.5 線目前最新的版本；之後要再拿修補得升 Boot 4
       （Spring Framework 7 / Jackson 3，屬於大改版，要另外評估）
